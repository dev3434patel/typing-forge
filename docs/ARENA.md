# Eight-person PHP arena

Source scope implemented2026-10-21. `/arena` and `/arena/:roomCode` are additive to the existing two-person human race. No new server runtime or WebSocket dependency is required. The transport interface uses bounded authenticated snapshot polling; all authoritative rules live in PHP/InnoDB. Persistent WebSockets require a separately provisioned host and are not claimed here.

## Lifecycle and trust

Authenticated POST `/arena/{create,join,get,ready,submit,leave,rematch,match,spectate,appeal}` uses the existing cookie session, CSRF/origin checks, expected-owner guard and rate limits. Import `backend/migrations/005_arena.sql` after the base schema. Rooms have at most eight distinct accounts and a unique seat index; each lifecycle update holds the room row and relevant membership rows in a transaction. Readiness requires at least two actual members and every occupied seat to be ready. The server then issues a three-second countdown, fixed text, English QWERTY comparison configuration, strict current-word editing and a shared15/30/60/120-second deadline.

`ArenaEvidence` validates every candidate with the unchanged `SessionValidator`, checks every issued comparison field, target equality, absence of pauses/extensions, authoritative start/deadline and immutable previously accepted event prefix. Competitive edits are individual keyboard graphemes; malformed or changed contracts are rejected. The server computes all progress, WPM, accuracy and placements from replay. A manual incomplete early finish forfeits the seat; it cannot establish a fast official finish. Client-local evidence remains exportable. Actual complete target finishes or the fixed deadline can finalize normally. Finish receipt grace is three seconds and never extends event timing.

Only finished, non-quarantined racers receive placements: descending credited characters, then descending input accuracy, then ascending completion duration. Equal triples share rank. Forfeits and quarantined results receive no placement. A silent participant has20 seconds from its last heartbeat to reconnect; afterward its latest accepted partial result is marked forfeit. Bounded polls back off while hidden or unavailable. Offline copy offers explicitly labelled bot practice rather than inventing a human result.

Matchmaking uses the median of up to20 accepted, non-arcade server-history scores, with a declared35WPM fallback when absent. The initial bracket is±10% of the room pace; it widens by five percentage points every ten seconds to a100% ceiling. A duration-level matchmaking row serializes public-room selection. Rematches require every remaining actual member to vote and create exactly one child room with a fresh issued text/start. Spectators receive public handles, member states and aggregate server metrics; no email, raw transcript or keystroke timing is serialized.

Public waiting lobbies use the same20-second heartbeat grace as active races. An absent host cancels the public lobby before matchmaking can assign another user. A silent nonhost frees its seat only while still `joined` in a never-started room, with no client session, attempts, replay, metrics or completion evidence. If at least two remaining live humans are already ready, removal starts the normal three-second server countdown. Private invitation rooms preserve their existing ten-minute waiting expiry; this housekeeping does not silently remove invited users. All decisions remain under the existing account→room→member lock order, without locking another account during room cleanup.

New-room creation inserts its host directly into slot 0 while the transaction exclusively owns the freshly inserted room and actor account. It does not first lock an empty `arena_members` index range. A native Apache capacity run exposed cross-room gap/insert-intention deadlocks in that former empty-range path; the failed receipt remains separate from this source correction. Existing populated-room joins and serialization retain current `FOR UPDATE` reads under the room lock, avoiding stale repeatable-read membership snapshots. No global retry, transaction-isolation change or seat-policy relaxation was introduced. A separately declared isolated Apache HTTP run passed 29/29 checks, including three simultaneous distinct-room creations with exactly one host in slot 0 for each. The corrected load allocated exactly 50 rooms/400 seats without create conflicts, but still failed the latency and error targets below. These observations do not establish hosted capacity.

## Plausibility review

The existing80-insertion/second burst cap and sustained500WPM/650-attempt-WPM limits are conservative automation heuristics. A valid replay that exceeds these limits, a reused event stream, or at least50 perfectly uniform insertion intervals is quarantined and excluded from placements. These checks do not prove human input or automation. Personal practice scoring is unchanged.

The affected account sees its own reason and partial metrics. It can record one review request timestamp; repeating that request is idempotent. This is a real operator-review record, without an invented moderator response or promised response time. Other members and spectators see only “Under review.” Retention and per-session deletion clear arena raw events/evidence through the existing account-data controls; deleting the account cascades its arena rows.
