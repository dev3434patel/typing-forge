## Implemented game

**Signal Run** is a self-contained word-gate journey, available at `/games` through the lazy [application route](../src/App.tsx), [navigation](../src/components/layout/Header.tsx) and [Games page](../src/pages/Games.tsx). A small network has lost its signal. The player opens 18 gates through three six-gate stages: The uplink, The crossing and The horizon. Each completed word lights a beacon in original lightweight SVG scenery. Later stages use longer English words. A small public word pool is shuffled locally with a deterministic seeded generator; replaying with another seed changes the order.

The player types the complete target word and explicitly opens the gate with Enter or a 44-pixel button. This keeps the action deliberate on desktop and touch screens and permits editing before submission. An overtyped or incorrect word cannot open the gate. Completing a word does not silently consume characters belonging to a later gate.

Calm journey has no deadline. The 60-second run starts only after its Start button is activated. Pauses exclude paused time; the current committed word and all accuracy evidence remain. The game pauses when its document becomes hidden or its window loses focus. Resuming is explicit. Restart creates fresh run state; ending a partial run produces an honest partial summary and does not set a local best.

There are no lives, daily rewards, purchases, rank changes or loss-aversion mechanics. Clean chains give a local sense of rhythm without adding speed, altering a race position or changing the typing product’s metrics. No extra dependency, remote game service, image download, WebGL renderer or audio engine is required. The game adds no 3D scene or choreography changes. The separate startup-cancellation lifecycle repair is documented in the [mobile input notes](MOBILE_INPUT_FIXES_2026-10-20.md).

Calm mode has no presentation interval. Paced mode refreshes its visible clock while active, and [SignalScene](../src/components/games/SignalScene.tsx) receives memoized gate progress so ordinary character attempts do not rebuild the decorative landscape.

## Accuracy and scoring contract

The game is not the main typing-session controller and does not write ordinary typing results. Its measurement is explicitly a **game character-attempt** contract:

```text
Input accuracy = correct inserted grapheme attempts / all inserted grapheme attempts × 100
```

Text is normalized to NFC and segmented with the product’s existing grapheme helper. The game diffs native edits to identify inserted and deleted characters. When a valid beforeinput range is available, it verifies that the range reconstructs the actual resulting text before using it. This counts a same-value selected replacement, which a text-only diff would otherwise miss. Invalid or mismatched range metadata falls back to the actual text change.

Every inserted grapheme is compared with the fixed word’s corresponding target position. Extra characters are incorrect. Replacing or deleting a mistake does not remove the original mistake from input accuracy. Deletions increase a separate deleted-character count and never create insertion attempts. An IME batch can contain several characters; no batch is called several physical keypresses and no per-key timing is inferred. Unchanged composition echoes do not add attempts.

A clean gate has zero incorrect insertion attempts for that gate. Correcting a mistaken gate can open it, but cannot make it clean retroactively. Clean-gate chains and their best length are independent from input accuracy. Gate progression, active time and accuracy remain separately visible. No WPM is manufactured from game interactions or comparisons with benchmark tests.

Pastes and drops are blocked in the input UI, with an input-event fallback. Replacement events identified by the browser as autocorrection mark the run assisted and exclude it from local bests, including unchanged visible text when no usable native range is available. In that case, assistance is retained without inventing character attempts; the clock still advances. Events at the exact deadline finalize the run before editing, and paused events remain ignored. Browser provenance is imperfect; this is not an anti-cheat system, identity verification or proof that a human produced input.

## Storage and offline scope

The game makes no backend, cloud-sync or database writes and does not save typing-session results. It listens to the existing session repository's owner-specific clear notification so a same-document privacy clear also discards game memory and the transient run. It stores at most one small game summary per mode under:

```text
sparowtype.signal-run.v1:<encoded owner scope>
```

Guest and signed-in owner scopes use distinct keys, and changing the owner remounts the entire game component. Only the mode, content version, gates, clean gates, accuracy, elapsed duration and pause flag are retained. Raw words typed by the player, draft text, account profile data and keystroke transcripts are not saved. The parser bounds storage input, checks summary values and discards unknown properties. Corrupt/incompatible data does not prevent play. Blocked storage falls back to the current visit’s in-memory record with an explicit message.

Completion re-reads the current persisted best and merges it with the visit's in-memory best before comparing a new run. This prevents an old tab's weaker result from replacing a newer stored best. Owner-specific storage events refresh the interface; a lower racing write is reconciled to the better known summary. Fixed serialization order avoids cross-tab rewrite loops. External clear events discard the in-memory best rather than restoring it. A failed read keeps the visit's result in memory and does not overwrite an unreadable stored value. This is local best-effort browser coordination, not a transactional cross-device score service.

Local bests compare gates, clean gates, accuracy, then active duration, in that order. Calm and paced records are separate. Paused records identify that pauses were used. Assisted, manually ended, active or empty runs cannot create a best. The UI labels records **This browser · unverified**, and explains that they do not enter typing history, WPM personal bests or public rankings. Browser-editable records are not trusted server evidence.

The game’s **Clear game bests** control removes only this owner’s game key and current in-memory game bests. [Workspace reset](../src/services/session-repository.ts) also removes the explicitly selected owner's game key, and acknowledged [account deletion](../src/services/account-data.ts) uses that owner-bound cleanup. [Sanitized game export data](../src/services/game-data.ts) is included by Settings and Profile, including a workspace with games but no typing sessions. These integrations preserve other owners' summaries and the existing server-acknowledgement requirement for account deletion. The [privacy page](../src/pages/Privacy.tsx) explains the game data scope. No actual user account data was deleted during implementation.

Clearing game bests in another tab refreshes the displayed records while preserving that tab's active game; completing it can establish a new best. Same-document workspace reset additionally discards the active game. This distinguishes removing saved bests from ending an ongoing session.

The game logic, English word pools, SVG and CSS are bundled locally. The [frontend deployment workflow](FRONTEND_DEPLOYMENT.md) includes Games in generated static routes and the site's scoped offline cache. After the required assets are cached, gameplay has no network dependency. A first-ever load without a connection still requires previously available assets. Static artifact, route, origin-outage and privacy evidence is recorded in the [upgrade audit](MOBILE_GAMES_STATIC_AUDIT_2026-10-20.md).
