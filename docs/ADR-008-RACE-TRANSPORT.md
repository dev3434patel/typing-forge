# ADR 008: PHP snapshots through SSE and POST, with polling fallback

Decision date: 21 October 2026. Status: implemented source; repaired race-clock behavior observed across four native browser engines in separately declared runs; capacity target failed and hosted capacity remains unverified.

The deployment artifact is a PHP hosting package. There is no confirmed VPS process manager or permission to install another application runtime. A Swoole/ReactPHP/Ratchet WebSocket process requires a persistent worker and suitable hosting; a Node WebSocket service requires another runtime and operational endpoint. Neither is silently assumed or installed. The chosen baseline is a typed `RaceTransport` interface with an optional SSE snapshot channel and existing authenticated POST event submission. Existing snapshot polling remains available before negotiation, on older endpoints, after stream failure, in hidden tabs, and on ordinary single-worker PHP development servers.

`raceTransport.subscribe` negotiates `/race/transport`; `raceTransport.submit` retains the existing canonical POST operation. The PHP capability response explicitly says two players and disables streaming on `cli`/`cli-server`, where a held stream could block the same process from accepting a submission. Other PHP SAPIs support the bounded stream unless `race_stream_enabled=false`. SSE support is not inferred from a fake connection badge.

`RaceStream` authorizes cookie identity, expected owner and room membership before opening its event stream. It releases the PHP session lock before waiting, holds no account/room transaction over a wait, limits each stream to 15 seconds, and uses a database advisory lock to bound one stream per owner. It rechecks account existence/auth version and emits authoritative room versions only. It does not use `Last-Event-ID` as authorization. There is no bearer token or secret in its query string. The ordinary API's origin/cookie guards still apply. Logout/account switching closes the client's owned subscription immediately; existing streams are bounded even if a client fails to close them.

The client waits for an actual owner/member/code/room-matching snapshot before replacing polling. Buffered/no-message handshakes have a four-second bound, failures close the old source and return to polling, reconnect attempts are bounded, stale versions/callbacks cannot replace newer state, and hidden/unmounted/account-switched subscriptions release their source and timers. A terminal snapshot closes streaming. Neither channel interpolates WPM into authoritative progress or changes race scoring.

No Redis dependency is needed for this single-database deployment. InnoDB continues to own race state; advisory locks bound stream ownership. HTTP/1.x browsers and shared PHP worker pools still impose connection/worker limits. Production support depends on reverse-proxy buffering, PHP worker capacity and HTTP/2 configuration; successful unit tests do not establish those properties.

Verification: 13 focused pure transport cases cover negotiation, fallback, buffered handshakes, stale delivery, wrong membership/code/room, owner cancellation, visibility, terminal state, and bounded reconnects. Existing race polling tests remain intact. At the initial combined checkpoint, **300 tests passed across five files**. The separate native Apache run described below exercised the supported handler; hosted/multi-region remains **UNVERIFIED**.

The existing room contract still has two participants. A separately versioned eight-person arena now has its own implementation and acceptance; this does not change the legacy two-person state machine, issuance, input policy or metrics. Its first isolated 50 rooms × 8 players capacity attempt completed 1,653 requests with p95 **943.1102ms**, so the requested 150ms target **FAILED** (`audit/2026-10-21/pack-backend-097e029bc5ccfaa2-arena.json`). The runner accidentally replaced that attempt's detailed report with its stdout summary; the summary/failure remain preserved. Exclusive receipt writes and distinct raw-report paths now prevent replacement, and a separately declared fresh attempt records this evidence-loss reason. The latest raw outcome belongs in the central final audit; no failed attempt is silently removed and no production rate limit is changed for the benchmark. Neither Arena capacity result establishes the SSE capability of a supported production PHP SAPI.

Primary references reviewed 21 October 2026: [MDN server-sent event usage and connection limits](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events), [MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource), [PHP session_write_close](https://www.php.net/manual/en/function.session-write-close.php). These establish protocol/session behavior; they do not prove the capacity of the user's host.

## Separate audit of threaded PHP

The retained CLI-server capacity run is not a production PHP worker-pool measurement. A separate opt-in runner uses the installed Windows Apache/PHP handler: a fresh loopback port, wholly owned configuration/PID/logs/document root, 64 request threads and 64 maximum connections on its own disposable database. It retains the application's deadlines and rate limits. No existing Apache configuration, service or user database is opened or changed. Native runtime proof confirms `apache2handler`, thread-safe PHP, the exact private ini/configuration and owned parent/worker identity (`audit/2026-10-21/pack-backend-d8941fa00279093f-apache-runtime.json`). Its initial Arena HTTP **27/27 checks** and password checks passed. After the first-host repair, a separately declared fresh instance passed **29/29 HTTP checks**, including three concurrent distinct-room creations with each host in its own slot0, and the password gate (`pack-backend-4678b38b84a8bd3f-arena-http-raw.json`). The earlier failure and its raw report remain retained.

The first threaded capacity run **FAILED**: 1,525 requests, p95 of successful responses **670.9726ms**, four create conflicts, and 328 rate-limited leave requests. The 1,200 requests/IP/minute policy is unchanged; this all-loopback workload exceeds that allowance. Inspection of the audit database's own InnoDB deadlock status established a cross-room empty-member-range gap-lock conflict during host insertion. A separate source repair inserts the first host directly under its newly created parent room; populated-room membership locks remain in place. The original raw report also contained a false-positive room-count assertion because sparse-array iteration skipped failed creates. A separate correction receipt records the actual **46 rooms/368 seats**; the harness now requires exactly 50/400 and preserves holes as failed allocations. The original raw report is retained unchanged (`pack-backend-d8941fa00279093f-arena-load-raw.json`, `...-capacity-assertion-correction.json`). These observations do not establish a sole cause for the measured latency or meet the 150ms target.

The separately declared repaired trial on fresh instance `4678b38b84a8bd3f` allocated exactly **50 rooms/400 seats** without create conflicts or evidence-timing 422 responses. It still **FAILED** the 150ms target: **767.406ms** p95 among successful requests, with 345 accepted submissions, 55 submission 429s and 400 leave 429s. The full 1,653-request workload used one unchanged 1,200/IP/minute bucket (`...-arena-load-raw.json`, `...-capacity-declaration.json`). A subsequent browser-account setup on that saturated bucket returned 429 before any browser was launched; the runner stopped its owned services gracefully and retained the failure/cleanup receipts. Browser acceptance therefore uses a separately declared fresh audit instance, with no capacity load or rate-counter reset. This does not convert the capacity failure into a pass.

Source inspection identifies two relevant serialization points: `Security::rate` performs an InnoDB upsert and read of the shared IP bucket; `ArenaService::handle` holds its room/member transaction while canonical evidence is validated and the response is serialized. Neither uses a filesystem JSON/flock limiter. The repaired trial's successful-submit phase nearest-rank p95 was **868.314ms**, versus create **103.3766ms**, join **88.3203ms** and ready **95.8423ms**. These phase measurements locate the slower operation but do not isolate its CPU/query/lock components. A dedicated hot-path profile is **NOT RUN**; changing limits, removing validation, or attributing all latency to hardware would not be supported by these receipts.

The first native four-engine browser group on build `b269bcf94045fe6da4f5` had **12 passes and four failures**, with zero retries/skips: account lifecycle, real sign-in and race authorization passed in all four engines; all four human-race progress cases failed. Countdown SSE snapshots intentionally omit unchanged room versions. `RaceSession` incorrectly treated the old snapshot's `server_now` as its mount-time clock, shifting finish wall time about three seconds behind canonical monotonic duration. Canonical validation correctly rejected this evidence. The repair passes the parent's calibrated server offset and fixes one wall/monotonic anchor at the authoritative start; snapshot age and later device wall-clock changes cannot move that run's elapsed clock. It preserves missed idle time and changes no validator tolerance, issuance or WPM formula. Four focused clock units pass; the actual pure PHP validator accepts four repaired checkpoint/timeout candidates and rejects the retained old-clock witness (**5/5**, `race-sse-clock-php.json`). Native confirmation is scoped separately below; the earlier failures stay in `pack-native-d8941fa00279093f-1792589183900-summary.json`.

On repaired build `3ffaa0a179b47e336a2d`, the separately declared fresh native group had **15/16 passes**, zero retries/skips (`pack-native-fee54c8191badf00-1792589930765-summary.json`). All four account lifecycles, real sign-ins and API race authorization/countdowns passed; Chromium, Edge and Firefox also passed the complete two-context human race, accepted progress in both directions and ordinary-clock 30-second settlement. WebKit's human-race case failed before room creation: its second context showed a successful sign-in toast but remained at the lazy-home `Suspense` fallback beyond the existing five-second Account-link assertion. This was distinct from the initial auth-owner preparation gate and from race evidence validation. A separately declared WebKit-only diagnostic with unchanged assertions/budgets, current accounts, no retries and no trace then **passed 1/1**, including both directions of confirmed progress and settlement (`pack-native-fee54c8191badf00-1792590307253-summary.json`). Thus the corrected human-race flow has passed in all four engines, while the original **15/16 run remains a failed run**, not a rewritten all-pass result. The cold-home delay did not reproduce; failure-only diagnostic resource capture did not run. Its cause, including the suggested interaction with service-worker precaching, remains **UNPROVEN**. No timeout or product behavior was changed to make that diagnostic pass.

The [Apache Windows documentation](https://httpd.apache.org/docs/2.4/platform/windows.html) describes its parent/threaded-worker arrangement. [PHP's Apache handler instructions](https://www.php.net/manual/en/install.windows.apache2.php) require thread-safe PHP and explicit module/ini configuration. Cleanup deliberately avoids `httpd -k shutdown`: [Apache's Windows MPM argument handling](https://github.com/apache/httpd/blob/2.4.x/server/mpm/winnt/mpm_winnt.c) can resolve a service for a `-k` operation before the separate configuration is read. The audit guard instead checks its exact owned parent/configuration and signals that parent's PID-specific shutdown event; any fallback is limited to revalidated owned process identities. Preparing this adapter does not establish a latency target or hosted availability.
