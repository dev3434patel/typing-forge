## Request admission

Previously every request consumed the same 1,200-per-minute IP bucket before authentication. Four hundred distinct accounts behind one network could exhaust that shared allowance while remaining within their own Arena budgets. The single counter row was also a serialization point; the historical measurement does not establish its share of the observed latency.

Only recognized `POST /arena/*` routes can use the new authenticated lane. `AuthService::user()` first verifies that the session account exists and its current database `auth_version` matches the session. The server applies the existing 300-per-minute Arena allowance once, before CSRF or body processing, and reuses that validated user for dispatch. This stricter allowance subsumes the generic 1,200-per-minute account allowance introduced in source21, avoiding its redundant database write. Authenticated malformed/invalid-CSRF requests also consume the 300 budget. Request bodies, `expectedOwner`, session IDs, and proxy headers cannot choose another identity. Missing, stale or deleted accounts retain IP accounting and cannot access protected operations.

The existing Arena budget remains 300 requests per minute, now keyed to the account across IP changes. Changing networks cannot multiply it. Room creation remains separately limited to ten per account per minute. Anonymous and authentication endpoint IP limits, CSRF checks, owner checks, authentication-version checks, body-size limits and competitive-evidence rules remain in force. Other API routes retain their existing IP policy. This change addresses shared-network fairness; it is not a general DDoS or multi-account abuse certification.

Every limiter increment now returns its exact atomic count through `LAST_INSERT_ID(expr)` and PDO `lastInsertId()`. A second shared-table read could observe a later request and reject a request that was within its own boundary. First insertion explicitly returns one; updates return their own increment. An older-window request cannot roll a newer bucket backwards. A missing counter result fails closed. The SQL remains an atomic upsert on the existing table and needs no schema migration.

MySQL documents connection-local counter generation as safe between concurrent clients; MariaDB documents that `LAST_INSERT_ID(expr)` returns the supplied value to the client. These are the mechanism references, checked 27 October 2026: [MySQL information functions](https://dev.mysql.com/doc/refman/8.0/en/information-functions.html), [MariaDB LAST_INSERT_ID](https://mariadb.com/docs/server/reference/sql-functions/secondary-functions/information-functions/last_insert_id). Actual application compatibility and timing still require the native acceptance run.

## Submission lock boundary

The complete existing candidate validation and competitive-input preflight now run before taking account and room transaction locks. Those checks depend on the authenticated owner and submitted immutable evidence, without mutable room reads. Invalid metrics or malformed evidence cannot occupy a room lock during full validation.

Before preparation, the service captures its receipt timestamp from the database clock. Initial submission settlement, event allowance, elapsed scoring and finish grace use that server receipt. Validation or lock waits cannot create additional eligible event time or consume a valid arrival's grace window. Request/body timestamps cannot replace the receipt. The final settlement and response still use the current database clock; mutable state closed by another accepted request remains closed. A reordered older checkpoint cannot lower an already accepted elapsed value, truncate its event prefix or replace newer evidence. Heartbeat writes use SQL `GREATEST` to retain a newer accepted liveness timestamp. Equal-time same-prefix interim checkpoints and exact finished retries remain valid without reopening terminal state.

The locked stage still checks the current membership, issued configuration, immutable event prefix, participant status, room state, authoritative shared start, server elapsed allowance and finish grace. It performs the separate authoritative-elapsed replay before writes. Candidate elapsed time and server elapsed time may differ; the first replay's metrics or chart are not substituted for server-clock projections. Finish idempotency, quarantine, final evidence and persisted canonical scoring retain the existing paths. Source21's lock-boundary repair did not change SessionValidator; source22 adds the replay-local optimization below. Neither changes scoring formulas, authoritative room start/deadline or 3D source. Receipt capture is an explicit backend timing-boundary repair; all timing source is not claimed byte-identical.

## Idle replay projection reuse in source22

Source22 changes `SessionValidator::replay` presentation work, preserving its formulas and accepted evidence. A single replay-local cached sample is keyed by the accepted event index, issued target text and final-finite flag. Unchanged idle buckets reuse alignment/counts, while every bucket still recomputes its timestamp, cumulative rates, local attempt rate and error delta. Edits, idle target issuance and final finite scoring invalidate the cached projection. The cache never crosses requests or reuses another participant's state. This follows the existing portable JavaScript replay behavior; it does not reuse a client-provided chart or widen accepted time.

The PHP differential corpus now includes six additional cases covering an 800-word target with long idle interim/final samples, idle issuance without a new edit, same-offset issuance anchors, pause/issuance boundaries and final finite reclassification. All chart entries, final metrics, character classifications, cursor and derived learning fields are compared with the actual portable implementation.
