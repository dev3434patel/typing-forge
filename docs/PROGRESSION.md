# Progression implementation and verification

Implementation date: 21 October 2026 (India). This document describes the new S1/S7 source, its actual checks, and the remaining acceptance work. It is not a claim of production account migration or browser acceptance.

## Trust and privacy contract

Typing metrics remain `forge-v3`. Progression is a separate projection. The browser recomputes completed, correctly committed characters and original insertion accuracy from canonical replay. A correct prefix of an unfinished word earns no XP. The native PHP projection uses the existing replay with `finiteFinal: true`; this removes partial-prefix credit while preserving correctly completed/submitted words. No scoring formula or input policy changed.

Device receipts are explicitly **local/unverified**, including account-owned offline games. Server claims send a session reference and calendar zone, not an XP/Keys/accuracy assertion. The server requires cookie authentication, CSRF, expected owner, a matching `Idempotency-Key`, an already accepted owner-bound session, unexpired raw evidence, and a fresh canonical replay matching the stored server payload hash. Human race rewards require a settled authoritative outcome. Actual server personal bests compare one exact server-approved cohort. Games without accepted server evidence never manufacture a verified position.

Claim IDs are unique per owner. Conflicting reuse is rejected. Account-row locks serialize concurrent rewards and spending. Derived receipts and command receipts rebuild award arithmetic deterministically; Keys entries are append-only and purchases refuse a negative balance. SQL foreign keys cascade progression owner data when an account is deleted. Device clear invalidates outstanding async work before clearing storage; stale hashing, queued writes, and sync acknowledgements cannot repopulate it.

**Retention qualification:** the existing 90-day raw replay retention is unchanged. Durable progression receipts hold aggregate key/finger/ngram counts, EWMA sufficient statistics, source payload hashes, and award facts, rather than another ordered passage/keystroke stream. They remain until cleared and are included in export. Once original raw evidence expires, a new verified claim is rejected; existing award arithmetic remains reproducible from immutable derived receipts. G5's perpetual raw-event recomputation is therefore **PARTIAL**, intentionally preserving the existing privacy boundary. Private custom text is not silently uploaded or duplicated.

The local and PHP source hashes use their respective stable serialization contracts. Cross-language parity checks compare numerical facts, identities and award state; they do not falsely assert that JavaScript and PHP serialize every float/empty object to identical SHA-256 bytes. The production server independently revalidates and compares its own canonical source hash.

**Session deletion boundary:** deleting a saved session removes its history/replay and the established adaptive/course/placement projections derived from that source. Previously earned progression receipts are a separate durable reward record: they retain owner-bound aggregate key/finger/ngram counts and timing, qualification facts and source hashes so earned quests, spending and idempotency remain coherent. These aggregates are personal learning data, not anonymous data. They can remain after that session is deleted. A device/workspace reset removes local progression; deleting the account removes verified progression through owner cascades. Keeping an award does not permit a new claim from a deleted source. Full erasure of every source-specific progression contribution on individual session deletion is therefore **PARTIAL**, explicitly disclosed; separating erasable skill contributions from frozen reward credits would require a versioned model rather than silently revoking Keys or invalidating earlier purchases.

Sync drops an explicitly deleted source's pending reference before any claim RPC, while preserving its existing reward receipt and ledger. A deleted session therefore does not remain in an endless unaccepted-source retry queue. This does not revoke an already verified award.

## Rules implemented

| --- | --- | --- |

| Levels/titles | Level 1 starts at zero; entering level `L+1` requires `floor(100 × L^1.35)` total XP; all thirteen requested titles through Mythic | Threshold inversion units + PHP mirror |
| Skills | Bayesian `(correct+1)/(n+2)`; problem keys need `n >= 20` and accuracy below .92; key/finger/bigram/trigram evidence; EWMA α=.2; independent `language|layout|method|policy` maps | Canonical projection + arithmetic parity; mixed-cohort isolation case |
| Timing | Only positive, contiguous individual keyboard intervals up to 2s; no invented within-IME/batch timing or timing across pauses | Projection source + focused cases |
| Receipts | Sufficient statistics preserve ordered per-session EWMA contribution without retaining the ordered text; receipt-boundary speed rounded to .001ms | TS incremental/rebuild and PHP numerical parity |

| Freezes | At most two, one quest-earned/one purchased; seven calendar days, expiry date exclusive; optional auto-use; missing days do not become fictional practiced days | Reducer cases + PHP parity |
| Repair | One qualifying ≥97% lesson repair within 48h of the broken boundary per streak lifetime; later break starts a new lifetime | Reducer + parity cases |
| Quests | Three deterministic unique daily templates, weak-key weighting, one free reroll before any daily reward, one weekly quest | TS/PHP seed/reward parity |
| Keys | Daily quest25, weekly75, qualifying lesson10, verified win15, game5–20; arcade Keys capped100/day; streak milestones50; known cosmetic spend only | Ledger/idempotency/spending cases |
| Badges | Six declarative bronze/silver/gold predicates with visible instructions and source receipt IDs | Reducer + PHP mirror |
| Leagues | Seven tiers; actual groups capped30; UTC week; top/bottom20% for groups≥5; earlier last-activity tie break; Bronze floor | Pure ordering units; one actual SQL-backed participant verified; concurrent full groups remain unverified |

| Reset safety | Owner generation captured before hashing, retained canonical source required, atomic reset tombstone rejects pre-reset starts, sync aborted on reset/auth change; an unwritable fallback cannot resurrect cleared in-memory state | Async service regressions plus cross-tab-marker/late-controller, corrupt metadata and blocked-storage cases |
| Dashboard | XP/title/streak/freezes, quests/reroll, weak keys, earned badges, real league data, wallet, cosmetic profile preview/equip, ledger, receipt export, focus-trapped level modal | TypeScript/source; browser acceptance pending |

The game daily cap is progression policy, not a change to the honest game score, canonical WPM, accuracy, or leaderboard eligibility. The added arcade Keys cap is an explicit anti-farming policy. A first observation establishes a PB baseline; it does not count as beating a previous result.

## Installation and integration

New SQL is `backend/migrations/002-progression.sql`, applied after `backend/schema.sql` to the intended application database by the deployment workflow. No migration was executed against the user's configured database during this implementation.

Backend autoload modules: `ProgressionCalendar`, `ProgressionQuests`, `ProgressionEngine`, `ProgressionFacts`, `ProgressionService`. `ProgressionService(PDO, SessionValidator)` exposes `get(user)`, `claim(user, body, idempotencyKey)`, `command(user, body, idempotencyKey)`, and owner `clear(owner)` for reset integration. The central backend entry point owns authentication/CSRF/CORS and the three `/progression` routes. Accepted source evidence remains in the existing session tables.

Frontend `ProgressionAccountAdapter(ownerId)` exposes `.load()`, `.claim(sessionId,timeZone)`, `.command(command)`. The central session-save hook invokes the lazy `claimProgression(result,{localOnly})`; accepted sync invokes `syncProgression(ownerId)`. Account sync sends only pending session references. Device reset/export integrates `clearProgression`/`exportProgression`. `/progression` is a lazy route. The generated PHP finger reference is checked against the existing shared keyboard maps by the parity harness; it is a reference finger assignment, not detection of a person's actual finger or hardware. `profile.skillMaps[scope]` separates language, layout, observed input method and scoring domain. `profile.skills` is a compatibility view of the first named scope; training must request its exact scope and must not merge these maps.

Reset retains only an owner reset timestamp/tombstone, with no previous evidence or balance. The timestamp is checked inside the primary transaction and against the fallback reset marker, including when another tab still caches an old source. A session that started before reset cannot add a new reward after reset. Completely blocked persistence cannot communicate a durable reset to another browser document; that environment is explicitly memory-only. If the device clock is moved behind its last reset timestamp, new local progression waits for a later valid timestamp; verified server rewards use server time.

Corrupt reset metadata is rejected before it can be rewritten. When no durable store accepts a requested clear, the visit retains an authoritative empty in-memory tombstone and the clear explicitly reports failure; it does not claim that an inaccessible stored copy was deleted. The user can retry when persistence is available.
